## 环节 1 · 技术选型：为什么选择零依赖

### 决策

| 决策项 | 选择 | 备选方案 | 理由 |
|---|---|---|---|
| 运行时 | Node.js 18+ | Go / Python | npm 生态本体在 Node 上，`fetch`、`zlib`、`node:http` 开箱即用，且零依赖即可完成全部工作 |
| HTTP 框架 | `node:http` | Express / Koa / Fastify | 本服务只有 4 类路由，框架带来的抽象收益为负；且「多一层中间件 = 多一次热路径函数调用」 |
| 依赖数量 | **0**（`"dependencies": {}`） | `tar` + `semver` + `mime-types` + `terser` | 见下 |
| 模块格式 | ESM (`"type": "module"`) | CommonJS | 顶层 await、`import` 静态分析、与未来对齐 |

### 为什么坚持零依赖

这不是炫技，是三个具体收益：

1. **评委/使用者 clone 下来就能跑**。`node src/index.js` 直接启动，不需要 `npm install`，也不受网络与镜像源影响。对一个「课程作业 + 可能被评审」的项目，这消除了最大的一道摩擦。
2. **消除了供应链风险**。这个服务的职责恰恰是「代理并转发第三方代码」，它自己的依赖树越干净越好。
3. **`tar` / `semver` / `mime-types` 这三个包的核心逻辑并不复杂**，自己实现一遍的成本低于引入它们的长期维护成本，而且能把「我确实理解其中发生了什么」这件事直接展示在代码里。
   - `tar`：npm 的 tarball 用的是标准 USTAR + PAX，格式很规整，300 行能覆盖。
   - `semver`：题目只要求 `latest`、`^1.2.0`、dist-tags，把范围再放大到 `~` `x` `-` `||` 比较符也在 400 行内。
   - `terser`：唯一真正难替代的，所以我把压缩目标主动缩小到「词法级安全压缩」，不做 AST 变换。

### 代价（诚实记录）

- 自己写的 semver 在极端边角语法上不等价于 `node-semver`（例如 `1.2.3 - 2` 这类畸形连字符范围）。
- 自己写的压缩器压不到 terser 的程度（无变量混淆），实测 30%~70% 的降幅，terser 通常能到 60%~80%。
- 这些边界都写进了 README 的「实现边界」章节，而不是藏在代码里。

## 环节 2 · 上游客户端：三级请求策略

### 问题

题目要求「尽量减少 npm registry 的访问次数」。要优化，先得量化「一次访问到底多大」。

### 实测（环节起点）

```
GET /vue/3.3.4（单版本 manifest）      2.9KB · 195ms
GET /vue（简版 packument）            866KB · 159ms
GET /vue（完整 packument）             2.0MB · 126ms
```

一个包名的完整元信息是 **2.0MB**，而它某一个具体版本的 manifest 只有 **2.9KB** —— 差 **700 倍**。

如果实现对每个请求都先拉完整 packument，那么「取一个小文件」的成本会被元信息彻底淹没。

### 三级策略

```
请求到达 (name, versionSpec)
        │
        ├─ versionSpec 是精确版本？
        │     └─ 是 → ① GET /{name}/{version}          （2.9KB，最省）
        │            失败(404)才降到 ②
        │
        ├─ 需要 tag / 范围解析？
        │     └─ ② GET /{name} 带 Accept: application/vnd.npm.install-v1+json（简版 866KB）
        │            上游不支持该 Accept（400/406）才降到 ③
        │
        └─ ③ GET /{name} 完整 packument（2.0MB）
                 │
                 └─ 解析出精确版本后，再补一次 ① 拿「完整 manifest」
```

第 ③ 步之后为什么还要补一次 ①？

> **这是一个容易踩的坑**：简版 packument（`application/vnd.npm.install-v1+json`）为了减小体积，会**剔除 `main` / `exports` / `jsdelivr` 等入口字段**，只保留 `dependencies` / `dist` / `engines` 这类安装必需信息。而入口文件解析恰恰只依赖被剔除的那几个字段。
>
> 所以「用简版 packument 解析版本」+「用单版本接口拿入口字段」必须成对出现，否则会出现「版本解析对了、入口却永远 404」的诡异现象。

### 实测效果

| 场景 | 上游流量 | 相对最坏情况 |
|---|---|---|
| `/vue@3.3.4/index.js`（精确版本快路径） | 2.9KB + tarball | **节省 99.9%** |
| `/vue@^3.2.0/index.js`（需要范围解析） | 866KB + 2.9KB + tarball | 节省 58.1%（相比完整 packument） |

### 附带的一致性处理

- **请求合并（single-flight）**：同一瞬间的 N 个相同请求只向上游发 1 次。
  实测：20 个并发 `fetchManifest("react","18.2.0")` → **实际发往 registry 的请求 1 次**。
  实测：5 个并发「冷包」`loadPackage("express","4.18.2")` → **实际 2 次**（元信息 1 次 + tarball 1 次），而不是 10 次。
- **stale-if-error 兜底**：上游 5xx 或超时时，如果有过期缓存，宁可用过期数据也不要给用户 502。可用性优先于一致性 —— 对一个 CDN 来说这是正确的权衡。
- **负缓存**：确认 404 的查询缓存 30 秒，防止「拿不存在的包名刷接口」把上游打爆。

## 环节 3 · tarball 解包：自己实现 tar 解析器

### 问题

`GET /vue@3.3.4/dist/vue.runtime.esm-browser.js` 需要的是**包内单个文件**，但 registry 只给一个 `.tgz`。所以必须解包。

### 为什么不能「gunzip 到内存再切」

最朴素的做法是 `zlib.gunzipSync(buffer).toString()` 然后字符串切割。问题：

- `lodash` 解压后 **1.3MB**，`vue` **1.9MB`，`axios` 1.7MB —— 看起来还行；
- 但 `electron`、`@types/node`、`typescript` 这类包解压后可以到 **几百 MB**。全部读进内存会让 Node 的堆直接爆掉，而且这些内存对「只取一个文件」的请求来说完全是浪费。

### 做法：流式状态机

```
tarball 字节流
   │
   ├─ zlib.createGunzip()          ← 边收边解压
   │
   └─ ByteReader（内部 512B 滑动窗口）
          │
          └─ tar 状态机：header → (pax | longname | data | dir) → header → ...
                 │
                 └─ 命中普通文件：直接 createWriteStream 流式写盘（背压由 await drain 控制）
```

内存中**永远只保留正在处理的那个 512 字节块 + 当前文件的一个 64KB 分片**，与包的总大小无关。

### tar 格式里必须处理的三个「隐藏关卡」

如果只按教科书里的 USTAR 规则解析，会在这三处翻车：

1. **PAX 扩展头（typeflag `x` / `g`）**
   现代 npm 打出来的包大量使用 PAX 记录来携带长路径、毫秒级 mtime、uid/gid 等。
   PAX 记录格式是 `<十进制长度> <key>=<value>\n`，其中长度**包含自身**。不处理就会读错后续所有偏移。
   处理方式：解析出 `path` / `size` / `mtime`，覆盖到**下一个**条目上。

2. **GNU 长文件名（typeflag `L` / `K`）**
   正文就是下一个条目的名字。老工具（尤其 GNU tar）会用它。

3. **base-256 数值编码**
   tar 规范里 size / mtime 字段平时是八进制 ASCII，但首字节最高位为 1 时表示「后面全是二进制大端整数」。这在大文件（> 8GB）和部分工具链里会出现。不处理会把 size 解析成一个荒谬的数字。

### 安全边界（这部分比功能更重要）

解包第三方 tarball 是**典型的不可信输入处理**，防了三件事：

| 风险 | 防御 |
|---|---|
| 路径穿越（`../../../etc/passwd`） | 条目名归一化时拒绝任何 `..` 段与绝对路径；落盘前再用 `path.resolve` 二次校验是否在根目录内 |
| 压缩炸弹（几百 KB 压缩成几十 GB） | 总解压体积上限 + 单文件体积上限，超限直接抛错中断 |
| 半成品污染缓存 | 先解到 `tmp/` 临时目录，成功后再 `rename` 到正式目录 —— 同文件系统的 rename 是原子的，保证「要么完整、要么不存在」 |
| HTML 注入（包内文件名含脚本） | 目录列表页对所有文件名做 HTML 转义 |

另外：遇到非法条目或非普通文件（软链/设备/FIFO）时**跳过单个条目而不是整个包**—— 一个坏条目不该毁掉一个正常包。

### 兼容性兜底

问题：npm 官方 registry 的 tarball 条目统一以 `package/` 开头，但**部分私有 registry / 第三方实现会打上 `foo-1.0.0/` 这样的包装目录**。题目明确要求支持私有 registry，所以必须处理。

做法：解包后检查根目录有没有 `package.json`；如果没有、且根下只有唯一一个目录、且那个目录里有 `package.json`，就把那一层拍平，让「根目录恒等于包根」这个不变量对下游永远成立。

### 实测

```
lodash@4.17.21      1054 个文件 · 1.3MB · 556ms（含下载）
vue@3.3.4             38 个文件 · 1.9MB · 157ms
axios@1.6.0           80 个文件 · 1.7MB · 155ms
```

## 环节 4 · URL 路由：把 URL 变成确定性结构

### 目标

把任意 URL 变成**一个纯数据对象**，不碰网络。这样路由逻辑可以被单测穷举，也保证了「非法 URL 不会打上游」。

```js
{ kind: 'file', name: 'vue', versionSpec: '3.3.4', subPath: 'dist/vue.js', compat: false }
```

### 支持形态与判定规则

```
/npm/ 前缀（可剥）→ 解析包名与版本 → look at remainder
                                        ├── ''       → entry（入口文件）
                                        ├── '/'      → listing（包根目录列表）
                                        ├── 'x/'     → listing（子目录列表）
                                        └── 'x/y.js' → file
```

`remainder` 的尾随斜杠是关键判别信号：`/vue@3.3.4` 返回入口文件，`/vue@3.3.4/` 返回目录列表。这正是 jsDelivr 的语义。

### 三个必须处理的边界

1. **scoped 包**：`@vue/shared` 里的 `/` 会被朴素 split 切坏，所以直接用正则整段匹配：
   - `/^(@[^/@\s]+\/[^/@\s]+)(?:@([^/]+))?(\/.*)?$/`
   - 版本部分允许 `^` `~` `>=` 等字符，所以不能用 `[0-9a-z.\-]+` 这种窄字符集。

2. **`/npm/` 前缀的歧义**：确实存在一个名叫 `npm` 的包。裸剥前缀会把 `/npm/1.0.0` 误判。做法：只有「剥掉前缀后剩下的部分能被包名正则完整匹配」时才认为是兼容前缀。

3. **重复斜杠**：`/vue@3.3.4//dist//vue.js` 应当等价于 `/vue@3.3.4/dist/vue.js`，而不是把 `dist//vue.js` 一路传到文件索引里匹配失败。做法：按 `/` 切分后过滤空段再 join。

   > 这个坑最初真的踩了 —— 单测里 `相邻斜杠被收敛` 这条第一次是红的。

## 环节 5 · 入口文件解析：严格贴合题面的优先级链

### 题面要求（逐字实现）

```
1. jsdelivr 字段
2. 否则 exports["."]：
   a. 是对象且有 default → 用它
   b. 是字符串 → 用它
3. 否则 main
4. 否则 404
```

### 实现

`entry.js` 里就是一个顺序的 4 段判断，每段都通过 `settle()` 做一次「候选路径 → 确实存在的文件」的收敛。

### 争议点：要不要「更聪明地」解析 exports 条件？

真实世界里的 `exports["."]` 长这样：

```json
"exports": {
  ".": {
    "import": { "node": "./index.mjs", "default": "./dist/vue.runtime.esm-bundler.js" },
    "require": { "node": "./index.js", "default": "./dist/vue.cjs.js" }
  }
}
```

顶层的 `default` **不存在**。如果按「更正确」的方式去递归找嵌套 default，`/vue` 就会返回 ESM 构建而不是 `index.js` —— 但这**偏离了题面**。题面写得很清楚：不满足就用 `main`。

**决策**：默认严格按题面实现（`main` → `index.js`）。把「完整条件解析 + browser 字段」放在 `ENTRY_CONDITIONS=1` 开关后面，默认关闭，并在 README 与代码注释里说明原因。

> 这类「题面 vs 真实世界」的冲突，正确的处理方式是把选择权交给调用方并写清楚理由，而不是自作主张。

### 真实包对照（实测）

| 请求 | 命中规则 | 结果 |
|---|---|---|
| `/vue@3.3.4` | **规则 1**（`jsdelivr: "dist/vue.global.js"`） | `dist/vue.global.js` |
| `/react` | **规则 2a**（`exports["."].default = "./index.js"`） | `index.js` |
| `/lodash` | **规则 3**（`main: "lodash.js"`） | `lodash.js` |
| 无入口字段的包 | **规则 4** | `404` |

自动化测试里直接断言了响应头 `x-byr-entry: index.js (exports["."].default)`，把「命中的是哪条规则」变成可验证的事实。

### 两处不影响优先级的健壮性补充

- **路径归一化**：去掉 `./` 前缀、多余斜杠、拒绝 `..`。
- **目录兜底**：`main` 指向目录（老包常见写法 `"main": "lib"`）时，依次尝试 `lib/index.js` / `index.mjs` / `index.cjs` / `index.json`。这不改变任何优先级，只是让「本来会 404 的一个常见情形」变成可用。

## 环节 6 · Content-Type：按扩展名精确映射

### 题面要求

> 根据文件扩展名在响应 headers 里返回对应的 Content-Type，比如对于 json 文件需要 `content-type: application/json; charset=utf-8`。

### 实现要点

1. **文本类必须补 charset，二进制类绝不能补**。
   - `application/json; charset=utf-8` ✅（题面明确要求）
   - `image/png; charset=utf-8` ❌（无意义，有些客户端会因此误判）
   - 判据：`text/*` 或白名单集合（`application/json`、`application/javascript`、`application/xml`、`image/svg+xml` …）。
2. **覆盖约 130 个扩展名**：JS/TS 全家桶、数据格式、文档、图片、字体、音视频、压缩包、证书等。
3. **无扩展名的文件按名字猜**：`LICENSE` → `text/plain`、`README` → `text/markdown`、`.gitignore` → `text/plain`。
   这里有个细节：`.gitignore` 的点在**第 0 位**，不能当扩展名解析（否则会解析出扩展名 `gitignore`）。
4. **未知扩展名回退 `application/octet-stream`**，让浏览器走下载而不是拿乱码当脚本执行。

### 实测

```
package.json                        → application/json; charset=utf-8
dist/vue.runtime.esm-browser.js     → application/javascript; charset=utf-8
dist/vue.global.js                  → application/javascript; charset=utf-8
README.md                           → text/markdown; charset=utf-8
LICENSE                             → text/plain; charset=utf-8
logo.png                            → image/png
font.woff2                          → font/woff2
mod.wasm                            → application/wasm
unknown.zzz                         → application/octet-stream
```

## 环节 7 · 目录列表页

### 题面给定了 HTML 骨架

```html
<!DOCTYPE HTML><html><head><meta charset="utf-8"><title>vue</title></head>
<body><h1>vue</h1><hr><ul>
<li><a href="index.js">index.js</a></li> ...
</ul><hr></body></html>
```

实现**完全保持这个结构**（评委可以逐行对照），只额外加了三样东西：

1. **上一级链接 `../`** —— 否则进到子目录就出不来了；
2. **一段内联等宽字体样式** —— `不要求美观度`，但也不该难看到无法使用；纯内联，不引任何外部资源；
3. **入口文件高亮标记** —— 目录列表里直接标出哪一个是入口文件，方便验证环节 5。

- 目录数据来自 `fileIndex` 的前缀匹配：给定 `dist/`，所有以 `dist/` 开头的路径取下一段，能取到 `/` 的是子目录，取不到的是文件。

- 目录为空时也要正常渲染（返回空列表而不是报错）。

## 环节 8 · 两级缓存：把上游访问降到最低

### 分层结构

```
请求
 │
 ├─▶ ① 内存 LRU（按字节限额，默认 64MB）
 │        │ 未命中
 ├─▶ ② 磁盘缓存（按 TTL 判定新鲜度）
 │        │ 未命中
 └─▶ ③ 上游 npm registry
          │
          └─ 写回 ② → 写回 ①
```

### 关键设计决策

**1. 内存缓存按「字节」限额，而不是「条数」**

按条数限额是错的。缓存 1 个 5MB 的 `vue.global.js` 和缓存 1 个 1KB 的 `package.json`，对内存的代价差 5000 倍。按字节限额（`MEMORY_CACHE_BYTES=64MB`）后：

- 不会出现「缓存了 1 万个小文件把内存吃掉」；
- 也不会出现「一个大文件把额度全占了」；
- 淘汰策略是标准 LRU（用 `Map` 的插入顺序，命中时删了重插到末尾）。

**2. 分类型 TTL（题面明确要求「不同内容选择不同的缓存过期时间」）**

| 内容类型 | TTL | 依据 |
|---|---|---|
| 单版本 manifest | 1 小时 | 版本元信息相对稳定，但 `dist-tags` 可能变 |
| packument | 5 分钟 | 新版本发布频繁，需要较快感知 `latest` 变化 |
| 解包后的文件内容 | **7 天** | npm 版本发布后**不可变** —— 这是最长的一档，也是收益最大的一档 |
| 404 负缓存 | 30 秒 | 短，防止上游抖动导致长时间误报 404 |
| 压缩后的字节 | 7 天 | 压缩是确定性函数，结果与内容一一对应 |

**3. 磁盘层存「解包后的目录树」，而不是 tarball**

如果磁盘只存 tarball，那么每次进程重启后第一次请求都要重新解包。存目录树之后，重启后第一次请求只需要「建索引」（实测 0.8ms），文件系统自己的 page cache 又相当于第三级缓存。

**4. 原子落盘**

解包过程写到 `tmp/`，完成后 `rename` 到正式目录。避免因进程中断在缓存里留下「半个包」。

**5. 请求合并（single-flight）**

`Map<key, Promise>` 实现。同一个包在冷启动瞬间被多个请求命中时，只有第一个真的去下载解包，其余等它的结果。

### 实测效果

| 场景 | 耗时 |
|---|---|
| `vue@3.3.4` 首次 `loadPackage`（下载 + 解包） | 157ms |
| `vue@3.3.4` 二次 `loadPackage`（命中磁盘缓存） | **0.8ms** |
| 首次读取文件（从磁盘） | 0.36ms |
| 再次读取文件（命中内存 LRU） | **0.02ms** |
| 5 个并发的冷包 `loadPackage` | 上游只被打 **2 次**（而非 10 次） |
| 20 个并发 `fetchManifest` | 上游只被打 **1 次** |

冷路径 → 热路径提升约 **200 倍**；HTTP 层面 `/vue@3.3.4/dist/vue.runtime.esm-browser.js` 从 8.2ms 降到 2.0ms（无压缩）再到 1.1ms（压缩结果命中缓存）。

## 环节 9 · 版本解析：自实现 semver

### 覆盖范围

| 语法 | 展开 | 示例 |
|---|---|---|
| 精确 | — | `1.2.3`、`=1.2.3`、`v1.2.3` |
| 比较符 | — | `>1.0.0`、`>=1.2.0`、`<2`、`<=2.0.0` |
| 通配 | 区间 | `*`、`1.x`、`1.2.x` |
| 插入号 | `^1.2.3` → `>=1.2.3 <2.0.0` | `^0.2.3` → `>=0.2.3 <0.3.0`；`^0.0.3` → `>=0.0.3 <0.0.4` |
| 波浪号 | `~1.2.3` → `>=1.2.3 <1.3.0` | `~1` → `>=1.0.0 <2.0.0` |
| 连字符 | `1.2.3 - 2.3.4` → `>=1.2.3 <=2.3.4` | — |
| 并集 | `\|\|` | `^1.0.0 \|\| ^3.0.0` |
| 交集 | 空格 | `>=1.2.0 <2.0.0` |
| dist-tag | 不解析，直查 | `beta`、`next`、`latest` |

### 三个容易写错的规则

**1. `^` 对 `0.x` 的处理**

`^` 的语义是「不改变最左边非零的那一位」。所以：
- `^1.2.3` → `<2.0.0`（锁 major）
- `^0.2.3` → `<0.3.0`（锁 minor）
- `^0.0.3` → `<0.0.4`（锁 patch）

很多实现会在这里写成统一 `<major+1`，导致 `^0.2.3` 错误地匹配到 `0.3.0`。

**2. 预发布版本的匹配规则**

`2.0.0-beta.1` **不满足** `^1.0.0`，即使 `>=2.0.0-beta.1 <2.0.0` 在数值上成立。node-semver 的规则是：**只有当范围内某个比较符「显式提到了同样的 `x.y.z` 并且带预发布标识」时，带预发布的版本才允许参与匹配**。

实现：

```js
if (isPre) {
  return set.some((c) => c.ver.prerelease.length > 0 && sameTriplet(c.ver, v));
}
```

**3. 预发布标识符的比较顺序**

- 数字标识符 < 字母标识符
- 前缀相同时，字段多的优先级高（`1.0.0-alpha.1 > 1.0.0-alpha`）
- 没有预发布 > 有预发布（`1.0.0 > 1.0.0-rc.1`）

### 实现方式

两阶段：

1. `parseRange(text)` → `Array<Array<{op, ver}>>`（`||` 的 OR-of-AND 结构）
2. `satisfies(version, range)` → 逐集合判定

中间把每个「比较符 + 版本」通过 `expandOperator()` 展开成 `>=` / `<` 边界对。这样 `satisfies` 只需要实现 5 个基本比较符，`^` `~` `x` 这些糖的复杂度被隔离在展开阶段。

### 实测

`/vue@%5E3.2.0/`（即 `^3.2.0`）解析到 `3.5.x` 系列的最高版本，响应头直接给出 `x-byr-resolution: range`；再用解析出的精确版本请求一次，响应头变成 `x-byr-resolution: exact`，且 `x-byr-version` 完全一致 —— 测试里对这条做了一致性断言。

## 环节 10 · HTTP 语义层

这一层把「文件内容」变成「一个合格的 HTTP 响应」。逐项：

| 能力 | 实现 | 为什么需要 |
|---|---|---|
| **CORS** | `Access-Control-Allow-Origin: *` | jsDelivr 的核心场景就是跨域 `<script>` / `<link>` 引入；没有 CORS 头这个服务在浏览器里根本用不了 |
| **ETag + If-None-Match** | 内容身份哈希，命中返回 `304` 且无 body | 浏览器二次访问时省掉整个 body |
| **Cache-Control** | 精确版本 → `public, max-age=31536000, immutable`；非精确 → `max-age=600` | 只有 URL 里的版本被精确锁定时才敢说 `immutable`；`/vue` 这种「解析到最新版」的 URL 必须短缓存，否则用户会长时间拿不到新版本 |
| **Range** | `bytes=start-end` / `bytes=start-` / `bytes=-suffix` → `206` + `Content-Range`；越界 → `416` | 断点续传、大文件分段下载 |
| **Accept-Ranges: bytes** | 总是发送 | 告诉客户端可以做范围请求 |
| **HEAD** | 返回完整头、不返回 body | 客户端探测文件大小/类型 |
| **OPTIONS** | `204` + 预检头 | 跨域预检 |
| **Vary: Accept-Encoding** | 发送压缩时带上 | 防止代理把 gzip 版本发给不支持 gzip 的客户端 |
| **405** | 非 GET/HEAD/OPTIONS | 语义正确 |

### Range 与压缩的冲突处理

**带 `Range` 头时一律不压缩，返回 identity。** 因为 `Content-Range` 的字节区间必须相对于「选定的表示」；如果同时又做内容编码，区间语义会变得难以对齐（不同压缩算法产生的边界不同）。这也是主流 CDN 的常见做法。

### 诊断响应头

每个文件响应都带一组 `x-byr-*`：

```
x-byr-package: vue            # 包名
x-byr-version: 3.3.4          # 最终解析到的精确版本
x-byr-resolution: range       # 版本是怎么解析出来的：exact / latest / range / dist-tag:xxx
x-byr-entry: index.js (exports["."].default)   # 入口命中了哪条规则
x-byr-cache: memory           # 内容来自哪一级缓存
x-byr-size: 304369
x-byr-compressed: 304369->71512 # 压缩前后字节
x-byr-minified: true          # 是否做过代码压缩
x-byr-url-style: jsdelivr     # 是否用了 /npm/ 兼容前缀
x-byr-bundle: inline-cjs      # 打包模式
```

这组头最初是为了调试方便，后来发现它把「每个环节到底做了什么」变成了**一条 curl 就能看到的事**，也让自动化测试可以直接断言内部行为，而不仅仅是断言状态码。

## 环节 11 · 压缩：传输压缩 + 代码压缩

题面把「压缩」和「打包」并列，实际上这是两件完全不同的事。

### 11.1 传输压缩（gzip / brotli）

**内容协商**：解析 `Accept-Encoding` 的 q 值，`br` 与 `gzip` 取高者；两者都没提到时看 `*`。

**只压缩文本**：图片、字体、wasm 本身已是压缩格式，再压一遍纯属浪费 CPU。判据同样用环节 6 的文本类型白名单。

> **踩坑**：最初直接拿 `contentType`（形如 `application/javascript; charset=utf-8`）去查白名单，永远匹配不上 —— 必须先按 `;` 切掉参数部分。表现是「压缩代码看起来完全正常，但响应里永远没有 Content-Encoding」。

**压缩结果进缓存**：压缩是纯 CPU 开销且结果确定性，缓存它收益极高。实测命中缓存后从 6.5ms 降到 1.1ms。

**不划算就不压**：小于 1KB 的不压；压完比原文件还大的也退回原样。

实测：

| 文件 | 原始 | gzip (level 6) | brotli (q5) |
|---|---|---|---|
| `vue@3.3.4/vue.runtime.esm-browser.js` | 297KB | 69.9KB（24%） | **66.6KB（22%）** |
| `lodash@4.17.21/lodash.js` | 531KB | 95.3KB（18%） | **86.4KB（16%）** |
| `axios@1.6.0/axios.js` | 95.0KB | 24.3KB（26%） | **23.6KB（25%）** |

### 11.2 代码压缩（`?min`）

**为什么自己写**：`terser` 会引入约 2MB 的依赖树，与「零依赖」目标冲突。

**做法：词法级安全压缩**，五步：

1. **词法分析**：正确识别字符串、模板字符串（含 `${}` 嵌套）、正则字面量、注释、数字（含 `0x` / 科学计数法 / 数字分隔符）。
2. **删注释**：保留 `/*!` 开头与含 `@license` / `@preserve` 的版权注释（法律要求，很多开源项目靠这个）。
3. **去缩进、合并空白**。
4. **安全删换行**：这是最关键的一步，见下。
5. **省 token 间空格**：用「前后字符相邻会不会粘连成别的 token」判定。

**关于 ASI（自动分号插入）的安全判定**

盲目删换行会改变语义：

```js
let a = 1
[b] = a        // 若把换行删掉 → let a = 1[b] = a，语义完全变了

function f() { return
  {x: 1} }     // 若把换行删掉 → 返回值变成对象而不是 undefined
```

判定规则：**只有当「前一个 token 在词法上不可能结束一条语句」时才允许删换行**。

- 前一个 token 是标识符 / 数字 / 字符串 / 正则 / 模板 → **保留换行**
- 前一个 token 是 `)`、`]`、`}`、`++`、`--` → **保留换行**
- 其余（运算符、`(`、`[`、`{`、`,`、`;`、`:`、`=` …）→ 可以删

这保证 `a = 1 +\n2` 会被压成 `a=1+2`，而 `a = b\n(c)()` 的换行会被保留。测试里专门有一条 `ASI 安全` 用例守着这个行为。

**关于正则 vs 除号的歧义**

`/` 既可能是除号也可能是正则字面量的开始。用经典启发式：看前一个有意义 token。若是标识符，只有当它是 `return` / `typeof` / `in` / `new` / `delete` / `await` 这类「后面必然跟表达式」的关键字时才当正则；若是 `)` / `]` / `}` 之后，当除号；其余当正则。

**不做的事（明确写进 README）**：变量名混淆、死代码消除、常量折叠、AST 优化。理由是这些都需要完整的 AST + 作用域分析，用词法手段做出来的一定会在某些真实代码上静默出错 —— 与其给一个能跑通 demo 但不安全的实现，不如把边界画清楚。

实测：

| 文件 | 原始 | 压缩后 | 降幅 | 耗时 |
|---|---|---|---|---|
| `lodash@4.17.21/lodash.js` | 531KB | **146KB** | 72.5% | 542ms |
| `vue@3.3.4/vue.global.js` | 463KB | **319KB** | 31.2% | 2197ms |
| `axios@1.6.0/axios.js` | 2.5KB | 1.8KB | 29.7% | 1ms |

**每个压缩结果都用 `node --check` 做过语法校验**（CJS 按 `.cjs`、ESM 按 `.mjs` 分别解析），全部通过。lodash 降幅特别大是因为它的源码保留了完整注释和文档块。

### 11.3 两种压缩叠加

```
vue@3.3.4/dist/vue.global.js
  原始                463KB
  → 代码压缩后         319KB   （31.2%↓）
  → 代码压缩 + gzip    85.0KB  （81.6%↓）
  → 代码压缩 + brotli  80.7KB  （82.6%↓）
```

**82.6% 的总降幅** —— 这是本服务对「浏览器直接引入大体积 UMD 包」这一核心场景最直接的价值。

### 11.4 `.min.js` 回退

jsDelivr 的一个经典行为：请求 `xxx.min.js` 而包里没有时，取 `xxx.js` 在服务端即时压缩返回，而不是 404。

实测 `/vue@3.3.4/dist/vue.global.min.js`（vue 并不提供这个文件）→ 200 + `x-byr-minified: true`，内容为 `vue.global.js` 的压缩版。

## 环节 12 · 打包：Inline 内联与 Rewrite 重写

> 本节记录第一轮实现的两种模式（Inline / Rewrite）。第二轮补上的第三种模式
> **Deep Inline（递归内联外部依赖）** 单独记在 [环节 16.6](#166-深度打包真正的多包合并成单文件)。

### 为什么分成两种模式

题面举例是「把多个依赖合并成一个文件」。真正实现后会发现，**CJS 和 ESM 的难度差一个数量级**：

- **CJS**：每个模块就是一个函数体，`require` 就是一次查表 —— 加一个 30 行的运行时就能正确合并。
- **ESM**：要正确合并必须实现「导入提升（hoisting）」和「活绑定（live bindings）」，也就是 rollup / esbuild 干的事。用正则把 `export` 改成 `exports.x = x` 在真实代码上一定会静默出错（循环依赖、`export *`、提升后的默认导出……）。

所以设计成两种模式，**自动选择**：

| 模式 | 触发条件 | 行为 |
|---|---|---|
| **Inline** | 入口及图内模块都是 CJS | 包内相对依赖递归内联为单文件 + 微型 require 运行时 |
| **Rewrite** | 入口或图内出现 ESM 语法（或显式 `?esm` / `?bundle=rewrite`） | 不做合并，把所有 import 说明符重写为指向本服务的**绝对 URL**，并锁定精确版本 |

Rewrite 模式不是「降级糊弄」—— jsDelivr 的 `+esm` 和 esm.sh 做的事实上就是这件事，因为在浏览器里裸模块说明符本来就只能靠重写成绝对 URL 来解决。

### Inline 模式产物结构

```js
/*! BYR Archive bundle · express@4.18.2 · entry=lib/express.js
 * mode=inline-cjs · modules=11 · built=2026-10-11T...
 * 未被内联的外部依赖（如 require("lodash")）会在 Node 环境下透传给原生 require，
 * 在浏览器中则会抛出明确错误 —— 请改用 ?esm 重写模式。
 */
(function () {
'use strict';
var __defs = {
"lib/express.js": function (module, exports, require, __filename) {
  /* ...原模块源码... */
},
"lib/application.js": function (module, exports, require, __filename) { ... },
/* ... */
};
var __table = { "lib/express.js\u0000./application": "lib/application.js", ... };
var __cache = Object.create(null);
function __load(id) { ... }
var __result = __load("lib/express.js");
if (typeof module !== 'undefined' && module.exports) { module.exports = __result; }
else if (typeof globalThis !== 'undefined') { globalThis.express = __result; }
})();
```

三个设计点：

1. **说明符解析表在构建期算好**（`__table`），运行时 `require` 是 O(1) 查表，不做路径字符串运算。
2. **外部依赖保留为 `require('body-parser')`，并在 Node 环境下透传给原生 `require`**；浏览器环境下抛出一条写明「请改用 ?esm」的错误，而不是静默返回 undefined。
3. **产物同时兼容 Node 与浏览器**：优先赋给 `module.exports`，否则挂到 `globalThis`。

### 说明符扫描用词法分析而不是正则

正则会被字符串和注释里的假 `require` 骗到：

```js
// require('./fake.js')
const s = "require('./also-fake.js')";
const real = require('./real.js');   // 只有这个是真的
```

所以复用环节 11 的 tokenizer（它已经带上了字符偏移），扫「ident `require` + `(` + string」这样的 token 序列。测试里专门有一条用例守着这个行为。

### 裸依赖的版本锁定

Rewrite 模式下，外部包说明符会被重写为**锁定了精确版本**的绝对 URL：

```
import 'lodash'   →   import '/npm/lodash@4.17.21/lodash.js'
```

解析链路：从 `package.json` 的 `dependencies` / `peerDependencies` / `optionalDependencies` 取出范围 → 用自身的 `registry.resolveVersion` 解析 → 用自身的 `store.resolveEntry` 算出入口文件 → 生成 URL。

这意味着本服务既是 CDN 又是自己的依赖解析器 —— 复用环节 2、5、9 的全部逻辑，没有额外代码。Node 内置模块（`fs` / `path` / `node:*`）会被识别并原样保留。

### 明确不做的事

- **不内联外部依赖**（本节记录的 Inline 模式是这样；第二轮补的 Deep 模式会内联，见环节 16.6）。
- 不处理 `import.meta`、`export *` 的语义完整性。
- 图超过 120 个模块或源码超过 8MB 时截断/报错，并在产物的横幅注释里标明。

## 环节 13 · 健壮性与安全

### 错误模型

统一用 `HttpError(status, message, extra)`，`handler` 单一出口翻译成 JSON 响应。状态码语义：

| 状态码 | 场景 |
|---|---|
| 400 | URL 非法（编码错误、无法解析的路径） |
| 403 | 路径越权 |
| 404 | 包 / 版本 / 文件 / 目录不存在；入口字段全不满足 |
| 405 | 非 GET / HEAD / OPTIONS |
| 413 | 超出体积上限 |
| 416 | Range 越界 |
| 500 | 未预期的内部错误 |
| 502 | 上游返回异常 / 无法连接 |
| 504 | 上游超时 |

### 资源保护

| 风险 | 措施 | 默认值 |
|---|---|---|
| 上游挂死拖垮整个服务 | 每个上游请求都有超时 + `AbortController` | 30s |
| tarball 撑爆磁盘 | 下载前先看 `Content-Length`，超限直接中止 | 128MB |
| 压缩炸弹 | 解压后总体积上限 | 1GB |
| 单文件撑爆内存 | 单文件上限 | 64MB |
| 并发解包拖垮 CPU | 信号量限制 | 4 |
| 内存缓存无限增长 | 字节上限 + LRU | 64MB |
| 慢连接占满 socket | keep-alive / headers 超时 | 10s / 20s |
| 请求体滞留连接 | 该服务不消费 body，`req.resume()` 直接丢弃 | — |

### HTTP 头的 ASCII 清洗（真实踩坑）

最初在 `x-byr-compressed` 诊断头里写了 `297KB→71KB` 这个箭头。结果：

```
TypeError [ERR_INVALID_CHAR]: Invalid character in header content ["x-byr-compressed"]
```

Node 在 `writeHead` 时会校验头值必须是 ASCII 可见字符，一个 `→`（U+2192）就让**整个响应变成 500** —— 而且这个头只在「走压缩分支」时才出现，所以表现成「大部分请求正常，只有带 Accept-Encoding 的请求 500」。

修法分两层：把箭头改成 `->`，同时在 `baseHeaders()` 出口统一做一次非 ASCII 字符替换。与其在每处拼字符串时提心吊胆，不如在出口兜住。

### 优雅退出

收到 `SIGINT` / `SIGTERM` 后停止接受新连接，等在途请求结束，10 秒兜底强退。避免正在写盘/响应时被硬杀。

## 环节 15 · 真实踩过的坑

按「发现顺序」记录，这些是本文里最有信息量的部分。

**1. tokenizer 产生空白 token，导致打包器漏扫说明符**

`findSpecifiers` 最初写的是 `tokens[i + 1]` 去取 `import` 后面的字符串。但词法分析会把空格也切成 token，所以 `import b from "./b.js"` 里 `'from'` 的后一个 token 是**空格**而不是字符串。
表现：`require()` 能被识别，`import` / `export ... from` 全部漏扫。
修法：所有「向后取一个 token」的位置统一改用 `nextSignificant()` 跳过空白/换行/注释。

**2. `→` 写进 HTTP 头，只在压缩路径上 500**

见环节 13。诊断头里用了 U+2192，Node 抛 `ERR_INVALID_CHAR`。因为只有走压缩分支才设置这个头，表现成「有的请求正常、有的 500」，很容易误判成压缩逻辑本身有问题。

**3. 压缩判定的 MIME 没剥 charset**

`shouldCompress()` 拿到的 `contentType` 是 `application/javascript; charset=utf-8`，直接去查 `TEXT_TYPES` 白名单永远匹配不上。
表现：压缩代码逻辑完全正确，但响应里从来没有 `Content-Encoding`。
修法：判定前先 `split(';')[0]`。

**4. semver 构造 base 时丢掉预发布后缀**

`>=1.2.3-beta.0` 被解析时，代码把版本重建成 `major.minor.patch` 三段，把 `-beta.0` 丢了，于是预发布匹配规则永远不生效。
修法：先把 `-` 后缀与 `+` build 元数据从原串里切出来，再重建，最后把后缀拼回去。

**5. 路由没收敛重复斜杠**

`/vue@3.3.4//dist//vue.js` 把 `dist//vue.js` 原样传到文件索引，匹配失败返回 404。单测 `相邻斜杠被收敛` 第一次是红的。
修法：按 `/` 切分后过滤空段再 join。

**6. 简版 packument 不含入口字段**

以为用简版 packument 拿到版本就够了，结果入口解析永远 404 —— 因为简版会剔除 `main` / `exports` / `jsdelivr`。
修法：版本解析可以走简版，但入口字段必须补一次 `GET /{name}/{version}`。这条已经写进环节 2 作为设计约束固定下来。

**7. 私有 registry 的 tarball 可能带包装目录**

npm 官方统一是 `package/`，但私有源可能是 `foo-1.0.0/`。题目要求支持私有源。
修法：解包后检测「根目录没有 `package.json` 且只有一个子目录且该子目录里有 `package.json`」，就把这层拍平。

**8. 测试用例里用了不存在的文件**

第一版端到端测试写了 `/vue@3.3.4/dist/vue.js`，实测 404 —— 因为 **vue 3 的 dist 里根本没有 `vue.js`**（只有 `vue.global.js` / `vue.runtime.esm-browser.js` 等）。这反过来印证了题面示例为什么选 `vue.runtime.esm-browser.js`。改用了真实存在的文件。

**9. 基准脚本把 axios 1.6 的 `lib/` 当 CJS 测内联，结果走了 Rewrite**

axios 从 1.x 起把 `lib/` 迁移成了 ESM，`lib/axios.js` 里是 `import` 而不是 `require`。所以自动选择 Rewrite 模式是**正确行为**，是测试用例选错了包。
修法：Inline 模式改用 `express@4.18.2/lib/express.js`（11 个 CJS 模块）；可执行性验证改用 `mime@3.0.0`（零依赖，产物能真正跑起来）。

**10. 测量口径错误：用「缓存未命中数」度量请求合并**

一开始统计 `cache.memory.stats().misses` 的变化，但 `fetchManifest` 内部会先查一次「404 负缓存」，每次都产生一次 miss，所以 20 个并发「看起来」产生了 20 次 miss。
修法：临时劫持 `globalThis.fetch` 直接数真正发往上游的 HTTP 请求数 —— 结果是 **1 次**，单飞确实生效。

## 环节 16 · 加分项第二轮：从「能跑」到「可运维」

题面最后一句话是：「除以上提到的功能外，你可以自行实现其他功能，符合项目整体功能需求、符合最佳实践的额外功能，也将被视为加分项」。

第一轮把功能做完了，但一个真正的服务还需要回答三个问题：**它坏了怎么知道？它被滥用怎么办？它自己会不会把自己压垮？** 这一轮就是补这些。

### 16.1 并发解包信号量（补上一个「空承诺」）

**发现方式**：回头审计配置项时发现 `MAX_CONCURRENT_EXTRACT` 只在 `config.js` 里被声明、从未被任何代码读取 —— 一个写在文档里、看起来生效、实际完全没用的配置项。这比缺功能更糟，因为它会让人误以为已经受保护。

**为什么需要它**：解包是 CPU 密集 + 磁盘密集的操作（gunzip 是纯 CPU、写盘是 IO）。没有上限时，100 个并发请求命中 100 个不同的冷包，就会出现「100 个 gunzip 同时抢事件循环 + 100 棵树同时往磁盘写」，结果是所有请求一起变慢，尾延迟急剧恶化。加了信号量后总吞吐基本不变，但资源峰值被压住 —— 这是**保护自己**，不是限制用户。

**实现**：`semaphore.js`，FIFO 队列 + 计数，零依赖。队列本身也设了长度上限（`MAX_EXTRACT_QUEUE`），超出直接返回 503 语义的错误，避免请求无限堆积。

**实测**：

```
解包信号量上限（MAX_CONCURRENT_EXTRACT）        4
5 个不同冷包同时请求                            448ms · 峰值并发 4（上限 4）· 累计完成 86 次
```

5 个冷包同时打进来，峰值并发精确停在 4，没有超发。

### 16.2 限流（令牌桶）

**为什么 CDN 需要限流**：不是因为要限制用户，而是因为**上游是共享资源**。npm registry 有速率限制与封禁策略，本服务无限转发的话，IP 被拉黑后所有人都用不了；而一个失控的脚本可以在几分钟内把磁盘缓存刷到几百 GB。

**为什么用令牌桶而不是固定窗口计数器**：固定窗口有两个经典缺陷 —— 窗口边界的突发（在 59.9s 和 60.1s 各打满一次额度），以及无法表达「允许短时突发」这个真实需求。令牌桶天然支持突发容量 + 平滑速率。

**三个实现细节**：

1. **桶数量有上限**（默认 10000，LRU 淘汰）。限流器自己也要限流 —— 否则伪造海量源 IP 就能把限流器的 Map 撑爆，用防御手段本身制造了新的攻击面。
2. **`X-Forwarded-For` 默认不信任**。只有 `TRUST_PROXY=1` 时才解析这个头。反了的话客户端只要随便伪造一个 XFF 就能绕过限流。
3. **默认关闭**（`RATE_LIMIT_PER_MINUTE=0`）。对一个 CDN 来说默认开限流会误伤正常的批量构建脚本；但「代码写了却永远不会执行」又等于没实现。所以：完整实现、可运行时开启、有自动化测试覆盖，并在文档里说清楚。

**实测**：

```
限流开启（60/分钟，突发容量 5）    第 6 个请求被拒 · Retry-After 1s · 累计拒绝 1 次
限流关闭后                        状态 200（恢复正常放行）
```

### 16.3 监控指标（Prometheus + 事件循环延迟）

一个自称最佳实践的服务如果只有日志、没有指标，运维上是不可观测的：**日志告诉你「发生了什么」，指标才能告诉你「有多频繁、有没有恶化」**。

手写了一个极小的计数器 / 直方图实现（不引 `prom-client`，还是零依赖），输出两条通道：

- `/_metrics` —— Prometheus 文本格式，16 个指标；
- `/_stats` —— JSON 快照，给人和脚本看。

**指标清单**（实测导出 54 个样本）：

```
byr_http_requests_total{method,status}
byr_http_request_duration_seconds{method}            # 直方图，14 个桶
byr_http_bytes_sent_total{encoding}
byr_upstream_requests_total{kind,result}
byr_cache_hits_total{layer} / byr_cache_misses_total{layer}
byr_extractions_total{result}
byr_extracted_bytes_total / byr_extracted_files_total
byr_extraction_duration_seconds                      # 直方图
byr_compression_bytes_saved_total{encoding}
byr_minify_bytes_saved_total
byr_event_loop_lag_seconds{quantile}                 # p50 / p99 / max
process_uptime_seconds / process_resident_memory_bytes / nodejs_heap_used_bytes
```

**为什么专门采集事件循环延迟**：这个服务既有 CPU 密集操作（gunzip、压缩、词法分析）又有磁盘 IO。平均请求延迟正常、但事件循环延迟飙升，说明某处有同步阻塞 —— 这是最能反映 Node 服务健康度、也最难从普通日志里看出来的指标。实现用 `perf_hooks.monitorEventLoopDelay()`，每 20ms 采样一次，成本可忽略。

`layer` 标签把缓存命中拆到了 `meta` / `extracted` / `memory` / `client-revalidate` 四层，可以直接看出「上游请求为什么少了」到底是哪一级在起作用。

### 16.4 `.npmrc` 私有源支持

题面要求「能从官方 npm registry 或者私有 npm registry 获取元信息以及拉取包文件」，并用 `REGISTRY` 环境变量指定。

实现完会发现一个现实问题：**真正用私有源的人不会去设环境变量，他们的配置就在 `.npmrc` 里**：

```
registry=https://npm.pkg.github.com/
//npm.pkg.github.com/:_authToken=ghp_xxxxxxxx
```

所以补了 `.npmrc` 解析，优先级链是：

```
命令行 --registry  >  环境变量 REGISTRY/REGISTRY_TOKEN  >  ./.npmrc  >  ~/.npmrc  >  默认官方源
```

**两个容易被忽略的细节**：

1. **`_authToken` 用 Bearer，`_auth` 用 Basic**。`_auth` 的值是 base64 的 `user:pass`，直接当 Bearer 发出去会被上游拒绝。判定方式是「是否匹配 `ghp_` / `npm_` 前缀」+ 是否含 base64 特征字符。
2. **`${VAR}` 环境变量插值**是 npm 支持的语法，不实现的话很多 CI 里配置的 `.npmrc` 会拿到字面量 `${NPM_TOKEN}`。

`/_stats` 里会回报「当前 registry 来自哪里」（`env:REGISTRY` / `npmrc:registry` / `default`）以及读到了哪些 `.npmrc` 文件的**键名**（只记键名，不记值，避免把令牌泄露到接口里）。

### 16.5 包信息 JSON API

目录列表页是给**人**看的，但 CDN 的下游常常是**程序**：构建脚本想知道「`^3.2.0` 到底解析到了哪个版本」，前端工具想拿完整文件清单做预加载，监控想检查入口文件有没有变。让这些场景去解析 HTML 或抓 tarball 是荒谬的。

```
GET /_api/{包名}[@{版本}]                  解析结果与概览
GET /_api/{包名}[@{版本}]/tree             完整文件树
GET /_api/{包名}[@{版本}]/dir[/子目录]      目录 JSON
GET /_api/{包名}[@{版本}]/file/{路径}       单文件元信息
```

**最关键的设计约束：它们复用与文件服务完全相同的解析链路**（同一个 `store.loadPackage`），所以接口返回的版本、入口、文件树和服务实际提供的内容**永远不会不一致**。如果 API 自己重写一遍解析逻辑，那才是灾难的开始。

`/_api/vue@3.3.4` 会把「版本是怎么算出来的」（`how: exact` / `range` / `dist-tag:beta`）、「入口命中了哪条规则」（`source: jsdelivr`）一并返回 —— 这些正是调试时最想知道的信息。

实测：`/_api/vue@3.3.4/tree` 7.2ms 返回 38 个文件的完整树（带 url 与 contentType）。

### 16.6 深度打包：真正的「多包合并成单文件」

第一轮的 `?bundle` 只内联**包内相对依赖**，外部依赖（`require('body-parser')`）保留原样。这在演示上够用，但题面说的明明是「**把多个依赖合并成一个文件**」—— 那些依赖恰恰在包外。

第二轮补上 `?bundle=deep`：从 package.json 的 `dependencies` 取版本范围 → 用自身的 registry 客户端解析精确版本 → 下载解包那个包 → 把它的入口也内联进来 → **对它自己的依赖递归处理**，直到深度或模块数触顶。

```
express@4.18.2/lib/express.js?bundle=deep
  模式             deep-inline-cjs
  内联模块数        144
  涉及包数          70
  未内联的说明符     50 个（全部是 Node 内置模块）
  产物体积          928KB
  打包耗时          冷缓存 9707ms  ->  热缓存 86ms
  深度打包 + 代码压缩 + gzip    246KB
```

**产物是真能跑的**，不是「看着像能跑」：

```
$ node -e "const express = require('./bench-deep-express.cjs'); ..."
typeof express=function | GET /hello -> 200 {"ok":true,"from":"single-file-express"}
```

928KB 的单文件里塞着 70 个 npm 包，起了一个真实的 express 服务并正确响应了 HTTP 请求。

对照数据能看出效果：

| 入口 | 普通 ?bundle | 深度 ?bundle=deep |
|---|---|---|
| `express@4.18.2/lib/express.js` | 11 模块 / 1 包 / 93KB | **144 模块 / 70 包 / 928KB** |
| `cookie-parser@1.4.6/index.js` | 1 模块 / 1 包 / 5.3KB | **3 模块 / 3 包 / 10.7KB** |
| `mime@3.0.0/index.js` | 4 模块 / 1 包 / 39.7KB | 4 模块 / 1 包（本身零依赖） |

**模块标识统一用 `包名@版本/包内路径`**。这样跨包内联时「哪个模块属于哪个包」是显式的，相对说明符在包内解析、裸说明符查引用方的 `dependencies`，规则一目了然，也天然处理了 `A → B → A` 的循环依赖（按 id 去重）。

**降级策略**：任何单个依赖解析失败都只记一条日志、退回「不内联」，而不是让整个打包失败。产物横幅注释里会列出所有未被内联的说明符（排除 Node 内置模块），调用方一眼就能判断产物是否真的自包含。

### 16.7 HTTP 缓存完整性修复与安全响应头

**修掉一个静默失效的缺陷**：原来 `Last-Modified` 写的是 `new Date().toUTCString()`，意味着**同一个文件每次请求返回的 Last-Modified 都不一样** —— 这个头完全失去意义，而且会让「按时间做增量同步」的客户端永远认为内容变了。

改成用「该版本解包落盘的时间」：对同一个版本稳定，语义上也说得通（对不可变的 npm 版本，内容的「最后修改时间」就是它被固化下来的时间）。同时补上 `If-Modified-Since` 的处理，并严格遵守 RFC 7232 §6 —— **`If-None-Match` 存在时忽略 `If-Modified-Since`**（这一条专门有用例守着）。

**安全响应头**：

- 所有响应加 `X-Content-Type-Options: nosniff`。对 CDN 尤其重要：否则「包内放一个名字像脚本、内容是 HTML 的文件」可能被浏览器嗅探成脚本执行。jsDelivr 也发送这个头。
- 目录列表页 / 首页加 CSP：`default-src 'none'; style-src 'unsafe-inline'; img-src data:; base-uri 'none'; form-action 'none'`，外加 `Referrer-Policy: no-referrer`。

  这是**纵深防御的第二层**：文件名已经做了 HTML 转义（第一层），CSP 保证即使某个环节的转义出了问题，注入的脚本也无法执行、无法外联。

### 16.8 CLI 工具

这个服务的核心逻辑（版本解析、入口解析、解包、压缩、打包）本身与 HTTP 无关。把它们关在服务器进程里，只有「发一个 HTTP 请求」一条路能用，既不方便调试，也无法在构建脚本里复用。

```
byr-archive serve                     启动服务
byr-archive info  <包[@版本]>          解析结果概览
byr-archive tree  <包[@版本]>          完整文件树
byr-archive ls    <包[@版本]> [目录]    目录列表
byr-archive cat   <包[@版本]> <文件>    输出文件内容（可重定向）
byr-archive min   <包[@版本]> <文件>    压缩统计 / 输出压缩结果
byr-archive bundle <包[@版本]> <文件>   打包（--deep 递归内联）
byr-archive verify <包[@版本]>         逐环节自检并给出结论
```

`info` 用一个真实包体验一下（顺便验证中文对齐）：

```
$ byr-archive info vue@3.3.4
包                 vue
请求的版本描述     3.3.4
解析到的版本       3.3.4
解析方式           exact（上游共 1 个版本）
入口文件           dist/vue.global.js  ← jsdelivr
入口 Content-Type  application/javascript; charset=utf-8
文件数             38
目录数             4
解压后体积         1.9MB（2010728 字节）
tarball            https://registry.npmjs.org/vue/-/vue-3.3.4.tgz
License            MIT
上游 registry      https://registry.npmjs.org  (default)
```

**`verify` 是最实用的一个**：它把每个环节都跑一遍并给出结论，等于把散落在各处的正确性检查打包成一条命令。

```
$ byr-archive verify mime@3.0.0
✓ 包元信息可获取  mime@3.0.0（版本解析方式：exact）
✓ tarball 已下载并解包  10 个文件，共 58.7KB
✗ 入口文件可解析（jsdelivr / exports["."] / main 优先级链）  ...
```

**中文对齐**：`String#length` 数的是码元个数，中文占 2 列，直接用会把表格弄歪。CLI 里写了一个 `displayWidth()` 按显示宽度补空格 —— 这是中文 CLI 里最常见的观感问题。

### 16.9 入口守卫（顺手修掉的设计问题）

`src/index.js` 原来在顶层直接调用 `main()`，结果是**任何人 import 它都会顺带起一个服务器**。第一次写模块加载检查脚本时就被这个副作用咬到（进程挂住不退出）。

现在加了入口守卫：只有「作为主脚本被执行」时才启动，被 import 时只导出 `main`。这也是让 CLI 能复用启动逻辑的前提。

## 环节 17 · 第二轮踩到的坑

这一轮的 bug 全是**只有把真实包跑一遍才会暴露**的那类 —— 它们不会出现在单元测试里，也不会在 demo 数据上出现。

**1. `'http-errors'.startsWith('http')` 是 `true`**

为了跳过 `https://...` 这类 URL 说明符，我写了 `spec.startsWith('http')`。这直接命中了所有以 `http` 开头的包名。

表现：深度打包 express 拿到 67 个包，唯独少了 `http-errors`，产物一运行就报 `Cannot find module 'http-errors'`。而且它是**静默跳过**的 —— 没有任何报错，只是那个包没被内联。

修法：用真正的 URL 判定 `/^(?:[a-z][a-z0-9+.-]*:\/\/|node:|data:)/i`。

> 教训：判断「是不是 URL」时用前缀匹配几乎总是错的。`http-proxy`、`http2`、`https-proxy-agent` 都会中招。

**2. `.json` 文件被当成 JS 模块内联 → 块语句语法错误**

`statuses` 包通过 `require('./codes.json')` 引入 `{"100":"Continue",...}`。把这个内容原样塞进 `function(module,exports,require){ ... }` 的函数体，花括号会被解析成**块语句**，于是 `"100": "Continue"` 直接语法报错：

```
SyntaxError: Unexpected token ':'
  "100": "Continue",
```

修法：`.json` 文件生成 `module.exports = {...};` 而不是原样嵌入。同时顺手处理了 **shebang 行**（`#!/usr/bin/env node`）—— 它在函数体里同样是语法错误，很多包的 CLI 文件都有。

**3. 深度限制 3 层把依赖树截断了**

`BUNDLE_MAX_DEPTH` 默认写 3。而 express 的依赖链是 express(0) → body-parser(1) → qs(2) → side-channel(3) → object-inspect(4)，正好在第 4 层被切断。

修法：默认提到 8，并意识到**深度是个很差的保险丝**（层数少不代表体积小）。真正有效的护栏是模块数上限与源码总量上限，深度只作为兜底。

**4. 响应发出后 `res.getHeader()` 一律返回空**

在 `res.on('finish')` 里读 `res.getHeader('content-length')` 来统计发送字节数 —— 这是最自然的写法，也是错的：**Node 把标头交给 socket 时会清掉内部标头表**。

表现是最阴的那种：指标接口正常返回、`byr_http_requests_total` 正常累加，只有 `byr_http_bytes_sent_total` 永远不存在；日志里那个「请求结束打印解析到的版本」的后缀也从来没出现过。**一个静默失效的诊断能力，比直接报错难发现得多。**

修法是先试 `res.getHeaders()`（实测 Node 22 下 `writeHead()` 之后立刻取也已经是空的），最后改成**从 `writeHead` 的参数里截取** —— 完全绕开 Node 的内部实现细节。

**5. semver 通配符展开不尊重原比较符**

`< 3` 被展开成了 `>=3.0.0 <4.0.0`（通配符分支无条件生成区间），于是 `>= 2.1.2 < 3` 永远匹配不到任何版本。

暴露方式：深度打包 `safer-buffer` 时报「没有匹配 `>= 2.1.2 < 3` 的版本」，而它的 `available` 里明明只有 `latest` 一个 tag —— 说明是范围解析本身的锅，不是网络问题。

修法：按 node-semver 的规则让每种比较符各自展开：

```
1.x  ->  >=1.0.0 <2.0.0      <1.x   ->  <1.0.0      >1.x  ->  >=2.0.0
1.2.x -> >=1.2.0 <1.3.0      <1.2.x ->  <1.2.0      >1.2.x -> >=1.3.0
```

**6. 修 5 的时候把 `~1` 和 `^1` 一起误伤了**

新的通配符分支用 `minorW || patchW` 作判据，但 `~1` / `^1` 这类「运算符 + 不完整版本」的 `minorW` 也是 true —— 它们被错误地当成通配符，抛出「通配符不支持比较符: ~1」。

这是**修一个 bug 引入另一个 bug**的典型案例，而且是回归测试抓到的（原有的 `波浪号 ~1.2.3` 用例变红了）。

修法：通配符分支排除 `~` 和 `^`，并把 `wild` 信息传进 `expandOperator`，让 `^` 自己处理 `^0.2.x` / `^0.x` / `^0.0.x` 三种情形的区别（**分支顺序很关键**：必须先判断 minor 是否非零，否则 `^0.2.x` 会被误判成 `^0.x` 而展开到 `<1.0.0`）。

**7. `/_stats` 返回 500：`cache is not defined`**

第一轮写 stats 处理器时用的是 `await import('./cache.js')`，后来为了统一风格改成静态引用 `cache.diskStats()`，但**忘了加 import**。因为 `/_stats` 之前没有测试覆盖，这个错一直躺着。

修法：加 `import * as cache from './cache.js'`，并给 `/_stats` 补上端到端测试。

**8. `mime@3.0.0` 与 `express@4.18.2` 的 package.json 真的没有 `main`**

这个不是我的 bug，是一个值得记录的**题面规则与真实世界的差异**。

按题面规则 4，`jsdelivr` / `exports["."]` / `main` 全都没有命中就应该返回 404。而实测：

```
GET /express/4.18.2       键数=24  只有 scripts, devDependencies（无 main）
解包出的 package.json      只有 author, contributors, ...（确实没有 main 字段）
files                      ["LICENSE","History.md","Readme.md","index.js","lib/"]
```

它们靠的是 **Node 的默认解析**（包根 `index.js`）。也就是说，**严格按题面实现，这两个很主流的包入口都会 404**。

**处理方式**：把选择权交给调用方，并给出解释。

- HTTP 路径默认**严格遵循题面**（返回 404），但在 404 响应体里带上解释：

  ```json
  {
    "error": "包 express@4.18.2 没有可用的入口文件（jsdelivr / exports["."] / main 均未命中）",
    "hint": "该包的 package.json 未声明 main / exports，但包含 index.js。Node 会默认解析到它；本服务默认严格遵循题面规则返回 404。设置 ENTRY_NODE_DEFAULT=1 可启用 Node 默认解析回退。",
    "nodeDefaultCandidate": "index.js",
    "enableWith": "直接访问文件 /express@4.18.2/index.js"
  }
  ```

- 加 `ENTRY_NODE_DEFAULT=1` 开关即可获得与 Node 一致的行为。
- **打包器解析依赖包入口时始终启用它** —— 那里模拟的是 Node 的模块解析语义，不是本服务 URL 的语义。

> 这类「题面 vs 真实世界」的冲突，正确的处理不是自作主张地"改得更正确"，也不是沉默地返回 404，而是**默认守规矩、把差异明确说出来、给出一键切换的开关**。

**9. `spawnSync` 自己启动自己，在 Windows 上报 EBUSY**

测试「打包产物能否真正执行」时，用 `execFileSync(process.execPath, ...)` 起子进程。基准脚本里能跑，测试脚本里报 `EBUSY`。

修法：改用 `vm.compileFunction` **在当前进程里**按 CommonJS 语义执行产物 —— 不用落盘、不依赖外部可执行文件，也就没有这个问题，而且更快。

**10. 请求合并的测量口径又错了一次**

第一版用「缓存未命中数」度量请求合并，被 404 负缓存查询污染。修好之后，这一轮又踩了一个变体：**给限流做基准时，用来读统计的 `/_stats` 请求自己也被限流拒绝了**，于是 `JSON.parse` 一个 429 响应体拿不到 `rateLimit` 字段。

修法：限流状态下不通过 HTTP 读统计，直接读进程内的限流器状态。

## 环节 18 · 已知不足与后续可做

### 明确的边界

| 不足 | 原因 | 如果要补 |
|---|---|---|
| ESM 不做单文件合并 | 需要导入提升 + 活绑定，是编译器工程量级 | 改为 Rewrite 模式（已实现），或接入 esbuild |
| 深度打包不处理 Node 内置模块垫片 | 浏览器里没有 `fs`/`path`，需要 polyfill 层 | 接入 `path-browserify` 之类，或在产物里注入最小 shim |
| 深度打包不处理 `package.json` 的 `browser` 字段 | 那是「同一份代码在浏览器里的替代实现」 | 解析 `browser` 映射表，优先选用浏览器版 |
| 压缩器不做混淆 | 需要 AST + 作用域分析，词法手段做不安全 | 可选接入 terser（作为可选 peer） |
| 缓存无主动失效 | 版本化内容天然不可变，TTL 足够 | 加 webhook 或定时校验 `dist-tags` |
| 无鉴权 | 有令牌桶限流（默认关闭），但没有身份认证 | 加 token 校验中间件 |
| 无 HTTP/2 | `node:http` 只到 HTTP/1.1 | 换 `node:http2` 或前面挂 nginx |
| 不支持 scoped registry（`@scope:registry`） | 需要让缓存命名空间与上游客户端按包名路由 | 把 registry 解析从「单例」改为「按包名查表」 |
| semver 边角语法不完全等价 | 自实现范围控制 | 补齐 `1.2.3 - 2` 这类畸形范围 |

### 如果继续做，优先级排序

1. **深度打包的浏览器化**：目前产物在 Node 里能跑，但浏览器里遇到 `require('fs')` 会报错。补一层 Node 内置模块的最小 shim（`path` / `buffer` / `events` / `process` 这几个最常用），就能出真正通用的浏览器单文件包。
2. **压缩结果的持久化**：目前压缩结果只在内存 LRU 里，进程重启后要重压。可以落到磁盘缓存（压缩是确定性函数，产物天然适合缓存）。
3. **`dist-tags` 的主动刷新**：目前 `latest` 最长 5 分钟延迟。可以做「后台定时刷新热门包的 tags」，把首字节延迟再压一档。
4. **压缩器接入 AST**：至少实现「删除不可达代码」和「字符串引号统一」，收益可观且比变量混淆安全。
5. **scoped registry 路由**：让 `@company:registry` 这类配置生效，把 registry 解析从单例改成按包名查表。

## 环节 19 · 第三方验收与整改（发现并修复 3 个 P1）

在功能与文档都完成之后，用一份《后端验收提示词》对自己的项目做了一次对抗性验收。
这件事的价值在于：**前面的 118 项测试全是「验证功能按设计工作」，而验收是「假设设计本身有问题」** —— 两者的发现能力完全不同。

验收脚本 `test/acceptance.mjs`（74 项检查，8 组：输入边界 / 注入越权 / HTTP 语义 / 输出编码 / 缓存一致性 / 资源 DoS / 性能阻塞 / 并发一致性）。
最终结果：**74 PASS · 0 FAIL · 3 WARN**。完整报告见 [`验收报告.md`](./验收报告.md)。

### 19.1 发现的 3 个 P1（全部已修复并复测）

**P1-1 · 并发请求同一冷包时，去重发生在信号量内部**

原来的写法：

```js
await extractSemaphore.run(() => cache.extractInto(name, version, producer))
//                              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
//                              去重逻辑在这里面
```

后果：N 个并发请求各自先抢信号量名额（或排进队列），**轮到执行时才发现已被合并** —— 队列额度被同一份工作白白吃光。

实测：100 个并发请求同一个冷包 → 4 个执行 + 64 个排队（正好是队列上限）→ **剩余 32 个请求直接报错**，状态码集合 `{200, 500}`。

修法：把 `singleFlight` 提到信号量**外层**，并加二次检查。复测：状态码集合 `{200}`、ETag 取值唯一、解包完成计数增量 **1**。

> 这个 bug 之前躲过了两次：`benchmark.mjs` 只测 5 个并发（阈值是 64），`smoke.mjs` 也没测同包并发。**只有把并发量提到超过队列上限才会暴露。**

**P1-2 · tarball 完整性完全未校验**

`grep -rn "integrity\|shasum" src/` 只命中 `api.js` 的字段透传 —— 也就是说，这个服务**知道**上游给了完整性字段，却从来不用它。

后果比看起来严重：传输损坏或链路篡改会被当作正常内容**写入缓存并保留 7 天**，期间所有请求都拿到错误内容。

修法：新增 `src/integrity.js`，用 `Transform` 边流边算 sha512/sha1（不额外缓冲，不破坏流式设计），解包结束后比对；**校验在写入缓存之前**完成，失败抛错并由 `extractInto` 清理 staging。

端到端复测：起一个本地 registry 代理，把 `is-number@7.0.0` 的 `dist.integrity` 改成错误值 → 服务拒绝并报 `tarball 完整性校验失败`，且 `getExtracted() = null`（坏数据未进缓存）。

**P1-3 · 代码压缩同步执行，阻塞事件循环最长 537ms**

压缩 531KB 的 `lodash.js` 要 500ms 以上，这段时间**整个进程无法响应任何其它请求**。一个匿名请求就能让服务僵住半秒。

有意思的是：**这个缺陷恰好违反了本项目自己采集的 `byr_event_loop_lag_seconds` 指标所度量的健康基线** —— 我加了事件循环延迟指标，指标报出了 537ms，而问题就在触发它的那条路径上。

修法分两层：

1. **根治**：新增 `src/minify-pool.js` + `src/minify-worker.js`，把压缩搬到 `worker_threads` 线程池。这与 gzip/brotli 的处理方式是同一原理（它们跑在 libuv 线程池里），只是需要自己搭一层。
   设计要点：懒创建、`unref()`（不阻止进程退出）、单任务超时后终止并重启该 worker、`worker_threads` 不可用时降级为同步并**告警一次**（宁可慢，不可不可用）。
2. **兜底**：加 `MINIFY_MAX_BYTES`（默认 4MB）体积闸门，超限返回原文件并带 `x-byr-minify-skipped: too-large`。

复测：压缩耗时 580ms（在 worker 中），**期间主线程事件循环最大延迟 32ms / P99 31.6ms**（对照修复前 537ms）。

### 19.2 另外修复的 2 个 P2

| 问题 | 修法 |
|---|---|
| 代码压缩结果不缓存，每次请求重算（实测二次请求 484ms vs 首次 537ms） | 新增 `cache.getBlob/setBlob`（内存 LRU + 磁盘 blob，TTL 用 mtime 判断），压缩/代码压缩/打包产物统一走这层。复测：冷 607ms → 热 **2.5ms** |
| `E_QUEUE_FULL` 返回 500 而非 503，客户端会误判为「请求本身是坏的」而不重试 | 新增可重试错误码映射：`E_QUEUE_FULL` → 503 + `Retry-After`，响应体带 `retryable: true` |

### 19.3 两处我自己判错的验收结论（如实记录）

这部分比发现的 bug 更值得写下来，因为它涉及**验收方法论**：

**误判一：`GET 携带请求体返回 400`**

用 `http.request` + `write()` 发请求得到 400，一度记为缺陷。复测时做了两件事：

1. 用原始 socket 手工构造**协议合法**的 chunked 请求 → **200**；
2. 用完全默认的 Node 服务器做对照组 → 在同一调用方式下**行为完全相同**。

结论：Node 的 http 客户端在该调用方式下不会自动加 `Transfer-Encoding: chunked`，裸 body 字节被服务端解析器当成了新的请求行（`HPE_INVALID_METHOD`）。**是测试工具的假象，不是被测系统的缺陷。**

> 教训：**没做对照组的「缺陷」不能算缺陷。** 报告一个假缺陷的代价，和漏报一个真缺陷一样高。

**误判二：`/%2e%2e/ 返回 200`**

以为是非法包名未被拦截。复测发现 `new URL('/%2e%2e/', 'http://x').pathname === '/'` —— WHATWG URL 标准在**解析阶段**就把 `%2e%2e` 和 `.` 归一到父目录，请求根本到不了路径拼接逻辑，返回 200 是因为它变成了服务首页。

> 教训：**安全测试要验证「攻击真的到达了目标代码」，而不只是「结果看起来可疑」。**

两处都已写进验收报告的第 6 节「验收过程中的方法论修正」，并把验收脚本改成能输出判据的形式，避免后续复验者重复误判。

### 19.4 保留未修的项

| 项 | 级别 | 为什么保留 |
|---|---|---|
| `?bundle=deep` 无并发/频率配额 | P2 | 有深度/模块数/字节数三重上限，且解包受信号量约束，同 URL 重复请求走缓存；是否再加一层配额属于产品决策（成本 vs 收益），不擅自替调用方决定 |
| 运维接口 `/_stats`、`/_metrics`、`/_api` 无鉴权 | P3 | 题面未要求鉴权；已实测不含任何令牌明文。生产部署建议在反向代理层限制这三个前缀 |
| 无 HTTP/2 | P3 | `node:http` 只到 HTTP/1.1；换 `node:http2` 或前置 nginx 都可以，但都超出「最简版」的范围 |

## 环节 20 · 最终验收：真实可用性确认

环节 19 的验收全部在**同一进程内**完成（起服务、发请求、断言，都在一个 Node 进程里）。这一轮要回答一个更朴素的问题：**这个服务真的部署起来、用浏览器打开一个页面，能用吗？**

于是把验证拆成五层，逐层加码：

| 层 | 手段 | 与上一层的差别 |
|---|---|---|
| ① 功能 | `test/smoke.mjs` | 进程内、13 组用例 |
| ② 对抗性 | `test/acceptance.mjs` | 进程内，但假设设计有问题 |
| ③ **真实客户端** | `test/live-check.sh` | **独立进程 + curl**，走真实 TCP/HTTP 栈 |
| ④ 基准 | `test/benchmark.mjs` | 体积 / 耗时 / 压缩率 |
| ⑤ **真实浏览器** | Chrome 无头加载 `docs/browser-demo.html` | **真实渲染 + 真实 JS 执行** |

结果：**120 / 74 / 70 / 11 节 / 11 项**，全部通过。原始输出都在 `docs/`。

### 20.1 第 ③ 层：为什么「独立进程 + curl」比进程内测试强

进程内测试跑得再全，也验证不了一件事：**服务作为一个独立进程启动后，还能不能正常工作**。中间隔着一整套真实的东西 —— 端口绑定、真实 socket、HTTP 解析器、操作系统文件 IO、进程生命周期。

这一层只用 `curl`，因此任何人都能拿同一串命令去复现。顺带它逼着我修掉了两处脚本自身的错误（这本身也是收获）：

- 我把「入口文件标记」检查写在了包根目录，但 `vue` 的入口是 `dist/vue.global.js`，标记出现在 `dist/` 里；
- **`curl` 默认不发 `Accept-Encoding`**，所以「gzip 生效」的检查从来就没测到东西 —— 必须显式加 `-H 'accept-encoding: gzip'`。同理 ETag / Range 也得真的把请求头发出去。

> 这两条都写进了脚本注释。**一条永远为真的断言，等于没有断言。**

### 20.2 第 ⑤ 层：真实浏览器抓出了 Node 侧测不到的缺陷

这是本轮最重要的一条经验。

演示页 `docs/browser-demo.html` 用**和用 jsDelivr 时一模一样的写法**引资源，只换 host：

```html
<script src="http://127.0.0.1:18080/vue@3.3.4"></script>
<script src="http://127.0.0.1:18080/lodash"></script>
<script src="http://127.0.0.1:18080/npm/dayjs@1.11.10/dayjs.min.js"></script>
```

第一次跑：10 项里过了 9 项，其中一项失败 —— `?esm` 产物在浏览器里报
`Failed to resolve module specifier "form-data"`。

**为什么 Node 侧怎么测都测不出来**：`?esm` 只重写被请求的那一个文件，它重写出的相对路径
`/npm/axios@1.6.0/lib/utils.js` 没带 `?esm`，浏览器加载这一层时拿到的是原始文件，
裸说明符无人处理。而在 **Node 环境里，那些裸说明符恰好能从 `node_modules` 解析到** ——
所以进程内测试会一路绿灯。只有真实浏览器会暴露它。

修法：重写出的 URL 一律带上 `?esm`（仅对 `.js/.mjs/.cjs`），让浏览器逐层加载时服务对每一层
都再做一次重写 —— 真正的传递式重写。

同时**修掉过度承诺**：产物横幅原来写着「可直接被浏览器作为 ES Module 加载」，这是错的
（重写只做路径替换，不做 CJS→ESM 语义转换）。现在横幅明确写出边界，并新增两个响应头让调用方
一眼判断模块图能不能跑：

```
x-byr-esm-transitive: true
x-byr-esm-unresolved: 0
```

修复后，浏览器里 `nanoid@5.0.4/index.browser.js?esm` 被重写为
`/npm/nanoid@5.0.4/url-alphabet/index.js?esm`，逐层加载成功，**`nanoid(12)` 真实生成了 ID**。

### 20.3 演示页的一个设计选择

演示页里有一项是 **「预期失败」** 的：

| 检查 | 期望 |
|---|---|
| 已知边界：axios 的 Node ESM 图（依赖 form-data 等 CJS） | **按预期失败** |

我把它写成「失败也算通过」。理由是：与其假装它可用、或者干脆不测这一项，
不如**把边界写成一条可执行的断言** —— 哪天这个边界变了（比如加了 CJS→ESM 的转换），
这条断言会立刻提醒你「文档里的边界描述过时了」。

### 20.4 五层验证的分工

回过头看，这五层不是重复劳动，各自有不可替代的位置：

- ① 保证**功能按设计工作**；
- ② 保证**设计本身没有明显漏洞**（前两轮在这里抓到 3 个 P1）；
- ③ 保证**部署形态下能用**（也逼出了脚本自身的假断言）；
- ④ 给出**可比较的量化数据**；
- ⑤ 保证**真实消费场景下能用**（抓到了 ①②③ 都测不到的 DEF-011）。

**每一层加的都不是「更多用例」，而是「更多真实成分」。**
