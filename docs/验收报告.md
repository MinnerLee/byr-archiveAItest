### 2.1 需求文档与项目背景的重大不一致（必须记录）

验收提示词的「项目背景」写的是**北邮人论坛 BBS 历史数据归档与检索系统**（数据接入、全文检索、任务调度），而本次提供的需求文档（飞书 wiki）是**实现一个最简版 jsDelivr**（npm registry CDN）。

两者在领域、技术栈、验收要点上完全不同。按提示词自身规则「若与本节冲突，以需求文档为准并在报告中注明差异」，本次验收**以飞书需求文档为唯一基线**，提示词中的 BBS 相关验收项（爬虫限速、断点续传、SQL 注入、全文检索性能、deep paging 等）**全部不适用**。

对应的等价替换如下（后续章节据此执行）：

| 提示词中的验收要点 | 本项目的等价项 |
|---|---|
| 数据正确性抽查（楼层数/作者/正文完整性） | 解包文件与上游 tarball 逐字节比对；tarball 完整性校验 |
| 分页丢帖 / 重帖 | 目录列表完整性；并发请求的 ETag / 响应一致性 |
| 重复导入破坏数据一致性 | 同一包重复解包的幂等性；缓存不产生半成品 |
| SQL 注入 | 无 SQL。等价项为**路径穿越**与**上游 URL 拼接注入** |
| 存储型 XSS（帖子正文回显） | 目录列表页对**包内文件名**的转义（文件名是外部输入） |
| 爬虫限速与封禁应对 | 上游请求合并、负缓存、解包并发上限、令牌桶限流 |
| 断点续传（导入任务） | 解包中断后的缓存原子性 |

## 4. 缺陷清单（阶段 2~6 产出）

共记录 10 项缺陷。**P0 = 0**。以下「修复状态」列中的复测证据均可在 [`acceptance-output.txt`](./acceptance-output.txt) 中 grep 到原文。

### 4.1 P1（严重）

#### DEF-001 并发请求同一冷包时，去重发生在信号量内部，导致队列被同一份工作占满

| 项 | 内容 |
|---|---|
| 级别 | **P1**（若线上常态出现 >64 并发请求同一个冷包，升为 P0：核心功能不可用） |
| 位置 | `src/store.js` `materialize()`（修复前约 108 行） |
| 复现 | 删除 `picocolors@1.0.0` 缓存目录后，对同一 URL 发起 **100 个并发请求** |
| 实际 | **状态码集合 {200, 500}**；32 个请求失败，错误 `解包队列已满（64/64）`；解包信号量计数 0→68（4 执行 + 64 排队，正是队列上限） |
| 根因 | 去重（single-flight）在 `cache.extractInto` **内部**，而信号量 `run()` 在它**外面**。N 个并发请求各自先抢名额、排进队列，轮到执行时才发现已被合并。队列额度被同一份工作白白吃掉 |
| 影响 | 热门包冷启动时部分用户直接拿到错误；且错误码为 500（见 DEF-005） |
| 修复 | 把 `singleFlight` 提到信号量**外层**，并加二次检查（`src/store.js` `materialize()`）。N 个并发请求只剩 1 个进入信号量 |
| 复测 | ✅ 100 并发：状态码集合 **200**；ETag 取值 **1 个**；解包完成计数增量 **1** |

#### DEF-002 tarball 完整性完全未校验

| 项 | 内容 |
|---|---|
| 级别 | **P1**（内容可信性；不构成越权，但会持续提供错误内容） |
| 位置 | 修复前 `src/` 全目录无任何校验逻辑 |
| 证据 | `grep -rn "integrity\|shasum" src/` 仅命中 `src/api.js:105-106` 的**字段透传** |
| 影响 | 传输损坏（CDN 边缘故障、代理截断）或链路篡改会被当作正常内容**写入缓存并保留 7 天**，期间所有请求都拿到错误内容；私有源场景下尤其危险 |
| 复现 | 起一个本地 registry 代理，把 `is-number@7.0.0` 的 `dist.integrity` 改成错误值，再把服务上游指向它 |
| 实际（修复前） | 服务正常返回 200，坏内容进缓存 |
| 修复 | 新增 `src/integrity.js`：边流边算 sha512/sha1（不额外缓冲），解包结束后比对；**校验在写入缓存之前**完成，失败即抛错并由 `extractInto` 清理 staging。可用 `VERIFY_INTEGRITY=0` 关闭 |
| 复测 | ✅ `loadPackage 抛出：tarball 完整性校验失败（is-number@7.0.0）：sha512(SRI) 期望 sha512-Bwc…`；且 `getExtracted(is-number@7.0.0) = null（未写入缓存）` |

#### DEF-003 代码压缩同步执行，阻塞事件循环最长 537ms

| 项 | 内容 |
|---|---|
| 级别 | **P1**（一个匿名请求即可让服务在该时段内停止响应任何请求） |
| 位置 | 修复前 `src/handler.js` 的 `serveFile()`（约 210 行） |
| 复现 | 请求 `/lodash@4.17.21/lodash.js?min`，同时读取 `/_metrics` 的 `byr_event_loop_lag_seconds` |
| 实际（修复前） | 压缩 531KB 耗时 537ms，期间**事件循环最大延迟 537ms**（P50 484ms） |
| 影响 | 对本项目自身采集的 ELD 指标构成直接违反：该指标存在的意义正是暴露这种阻塞 |
| 修复 | 新增 `src/minify-pool.js` + `src/minify-worker.js`：把压缩搬到 `worker_threads` 线程池（默认 `min(cpu-1, 4)` 个 worker，懒创建、`unref()`、单任务超时重启、不可用时降级为同步并告警）。同时给 `?min` 加 `MINIFY_MAX_BYTES`（默认 4MB）体积闸门，超限返回原文件并带 `x-byr-minify-skipped: too-large` |
| 复测 | ✅ 压缩耗时 580ms（在 worker 中执行），**期间主线程事件循环最大延迟 32ms / P99 31.6ms**（对照修复前 537ms） |

#### DEF-005 可重试的暂时性失败返回 500 而非 503

| 项 | 内容 |
|---|---|
| 级别 | P2 |
| 位置 | `src/handler.js` `sendError()` |
| 证据 | DEF-001 的复现中，错误响应状态码为 500，body 无 `retryable` 标记 |

#### DEF-006 `?bundle=deep` 无并发或频率配额（DoS 面）

| 项 | 内容 |
|---|---|
| 级别 | P2 |
| 复现 | 匿名请求 `/express@4.18.2/lib/express.js?bundle=deep` |
| 实测 | 冷请求 174ms~9.7s（视缓存），产物 928KB，涉及 **70 个包**；该操作可被任意匿名者触发，每次都要下载并解包整棵依赖树 |
| 现状 | 只有「最大深度 / 最大模块数 / 最大字节数」三个上限，**没有**「并发打包数」或「每客户端打包频率」限制 |
| 影响 | 并发请求不同包的 deep bundle 可造成 上游压力 + CPU 峰值。**部分缓解**：同 URL 重复请求命中缓存（冷 174ms → 热 67ms）；70 个包的下载与解包受既有解包信号量约束 |
| 修复建议 | 复用已有的 `ratelimit` 对 `?bundle=deep` 单独设一条更低频的配额；或对 bundle 操作再套一层小并发信号量（默认 2） |
| 状态 | ❌ **未修复**（保留，成本/收益需产品决策） |

## 6. 验收过程中的方法论修正（必须公开记录）

按铁律 3（可复现）与铁律 8（范围诚实），如实记录两处**我自己判错并纠正**的项：

### 修正一：`GET 携带请求体返回 400` —— 判定为「非缺陷」

- **初始判定**：FAIL（疑似服务不能正确处理带 body 的请求）
- **复测方法**：用原始 socket 手工构造**协议合法**的 chunked 请求，同时用完全默认的 Node 服务器做对照组
- **复测结果**：合法 chunked 请求 → **200**；对照组（默认 Node 服务器）在同一调用方式下**行为完全相同**（`HPE_INVALID_METHOD`）
- **真实原因**：Node 的 `http.request` + `write()` 在该调用方式下不会自动添加 `Transfer-Encoding: chunked`，导致裸 body 字节被服务端解析器当成新的请求行 —— 是**测试工具的假象**
- **最终判定**：**非缺陷**。已在验收脚本中改为用原始 socket 复测，并保留该结论的推演过程

### 修正二：`/%2e%2e/ 返回 200` —— 判定为「非缺陷，但需说明判据」

- **初始判定**：WARN（疑似非法包名未被拦截）
- **复测结果**：`new URL('/%2e%2e/', 'http://x').pathname === '/'` —— WHATWG URL 标准在**解析阶段**就把 `%2e%2e` 与 `.` 归一到父目录，请求根本到不了路径拼接逻辑；返回 200 是因为它变成了服务首页
- **最终判定**：**非缺陷**。已在验收脚本中把该用例改为显式验证归一化行为并输出判据，避免后续复验者重复误判
